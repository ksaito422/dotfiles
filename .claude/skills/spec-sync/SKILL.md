# 仕様書・チェンジログ同期

## 使い方

機能追加・仕様変更のセッションの区切りで、変更内容をドキュメントに反映してほしいと頼まれたときに使う。

なぜこの手順が要るか: 実装の詳細をそのままドキュメントに貼ると、後で読む人(未来の自分やチームメンバー)にとって「何が変わったか」が埋もれてしまう。既存のファイル・フォーマットを確認してから、利用者視点で要約して追記することで、ドキュメントが実際に使える状態を保てる。

## ワークフロー

### ステップ1 — 変更内容を把握する

`git diff` / `git log`や、この会話でここまで実装した内容から、何が変わったかを整理する。単なる実装の詳細ではなく、「何ができるようになったか」「何が変わったか」という利用者視点の変更点を抽出する。

### ステップ2 — 対象ドキュメントを特定する

プロジェクト内の仕様書ファイル(`spec.md`、`docs/spec.md`、`SPEC.md` など)とチェンジログファイル(`CHANGELOG.md`、`docs/changelog.md` など)を探す。見つからない、または複数候補がある場合はユーザーに確認する。ファイル名やパスを決め打ちしない。

### ステップ3 — 仕様書を更新する

既存の見出し構成・文体・粒度に合わせて、該当セクションに変更点を追記または修正する。新しい概念であれば適切な見出しを追加するが、既存の構成は崩さない。

### ステップ4 — チェンジログに追記する

既存のフォーマット(日付の書き方、箇条書きスタイル、カテゴリ分けなど)に合わせて新しいエントリを追加する。実装の詳細をそのまま貼り付けるのではなく、変更点を簡潔に要約する。

### ステップ5 — 差分を報告する

更新した内容を簡潔にユーザーへ報告する。

## 出力フォーマット

```markdown
## ドキュメント更新
- **spec.md**: [追記・修正したセクションと概要]
- **CHANGELOG.md**: [追加したエントリ]
```

対象ファイルが見つからず作成が必要だった場合や、ユーザーへの確認が必要だった場合はその旨も記載する。

## アンチパターン

1. **フォーマットを無視した追記**: 既存の文体・見出し構成・箇条書きスタイルを踏まえずに追記しない。
2. **実装詳細のコピペ**: コードの変更点をそのまま貼るのではなく、利用者にとって意味のある変更として要約する。
3. **ファイルパスの決め打ち**: 仕様書・チェンジログのファイル名やパスをプロジェクトごとに確認せず固定しない。
4. **既存エントリの上書き・削除**: 過去の記録を消さず、追記する。
