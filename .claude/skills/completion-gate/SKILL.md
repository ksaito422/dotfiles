# 完了ゲート

実装タスクの完了判定を担うワークフロー。「テストが green になった」時点ではなく、簡潔化とレビューを通過して must 指摘がゼロになった時点で完了とする。レビューは skill `review-pr`（レベルは **`low` を明示指定する** — review-pr の既定が変わってもゲートのコストが暗黙に変わらないようにするため）に、簡潔化はビルトイン skill `simplify` に委譲し、このスキルの責務は順序制御と完了判定のみ。

## 手順

### 1. 前提条件の確認

対象の変更がすべてコミット済みであることを確認する（`review-pr` は未コミット差分を優先するため、ゲート対象の差分を確定させる）。未コミットの変更が残っていれば skill `commit` の規約に従ってコミットしてから開始する。

PR は不要（`review-pr` はローカル差分で動作する）。

### 2. 簡潔化（simplify）

skill `simplify` を実行し、変更コードの重複・不要な抽象・冗長な記述を修正する。

- 修正を適用したら関連テストを実行して green を確認し、`refactor:` としてコミットする
- 修正対象がなければスキップする

### 3. レビューループ（must ゼロまで）

1. skill `review-pr` を引数 `low` で実行する
2. `review-pr` が must として表示または判定保留と伝えた所見が 0 件なら、ループを抜けて手順4へ（must の判定の定義は `review-pr` 側に従う。判定保留の must は解消済みと扱わない）
3. must を修正する。指摘1件 = 1コミットに分割し、修正のたびに関連テストを実行して green を確認する
4. 1 に戻って再レビューする

must がゼロになるまで反復する。回数では打ち切らない。ただし進捗がない場合 — 同じ must が2周連続で解消できない、修正しても同じ指摘が再出現する、または修正に仕様判断が必要な場合 — はループを中断し、残った must を列挙してユーザーの判断を仰ぐ（この場合タスクは完了とならない）。

must の偽陽性は一次的には `review-pr` 側の反証検証（REFUTED の除外）が受け持つ。それをすり抜けた must を偽陽性と判断できる根拠（矛盾するコード行・既存のガード）がある場合は、黙って無視せず、修正もせず、根拠を添えてユーザーに確認する。ユーザーが偽陽性と認めた must は解消済みとして扱う。

### 4. 完了報告

- ask / imo / nits は修正せず、一覧でユーザーに報告する（対応するかはユーザー判断）
- must ゼロを確認した時点で初めて「実装タスク完了」と報告する

## 備考

- must の修正で新たなテストが必要な場合は [tdd](../tdd/SKILL.md) に従って進める
