# エラー・不整合診断

## 使い方

以下のいずれかが会話に含まれたら適用する:
- スタックトレース / 例外メッセージ
- コマンド・ビルド・テストのエラー出力
- 期待した値と実際の値が食い違っている報告(数値、動作、表示など)
- 「これは何?」「なぜ?」「対応して」「エラーになった」という短い指示とともに貼られたログ

なぜこの手順が要るか: エラーを見た瞬間に思いついた修正を当てると、根本原因を外して同じ不具合を再発させたり、無関係な箇所を壊したりしやすい。再現条件の確認と検証を挟むことで、修正が実際に効いているかを確認できる。

## 診断ワークフロー

### ステップ1 — 再現条件を確認する

何をしたときにこの結果が出たか(コマンド、操作手順、入力)を特定する。会話に明記されていなければ、直前のやり取りや直近の変更から推測してよいが、曖昧なままステップ2に進まない。一度きりの偶発的事象か、毎回再現するものかも見極める。

### ステップ2 — 手がかりを集める

- 関連する設定ファイル、バージョン情報、直近のコード変更(`git diff`、`git log -p` など)を確認する。
- 環境固有の要因(OS、パッケージバージョン、実行環境の違い)がないか確認する。
- 対象領域の既知の挙動(フレームワークの仕様、DBのプランナ、ビルドツールの仕様など)を踏まえる。

### ステップ3 — 原因仮説を立てる

集めた手がかりから、最も可能性の高い原因を挙げる。確信度が低い場合はそう明言し、複数の仮説がある場合はどれから検証するか順序を示す。仮説を1つに決め打ちして次に進まない。

### ステップ4 — 検証する

仮説を確かめる最小限の方法(ログの追加、再現コマンドの実行、該当コードの確認など)を実行する。検証できない場合は、その旨とユーザーに確認したい点を明示する。

### ステップ5 — 修正する

検証で裏付けられた原因に対して修正を行う。原因が特定できていない状態で「とりあえず」の変更はしない。

### ステップ6 — 再検証する

修正後、ステップ1で確認した再現条件を使って問題が解消したことを確認する。再現条件を再実行できない場合は、その旨と代替の確認方法をユーザーに伝える。

## 出力フォーマット

```markdown
## 原因
[何が原因だったか、根拠とともに]

## 対応
[何を変更したか。ファイル:行 で具体的に]

## 検証結果
[再検証の結果。できなかった場合はその理由]
```

原因が複数考えられ絞りきれない場合は、検証した仮説と却下した仮説をそれぞれ簡潔に記載する。

## アンチパターン

1. **再現条件を確認せずに修正すること**: 何が起きたかを特定する前にコードを変更しない。
2. **決め打ちの修正**: 「たぶんこれだろう」で仮説を1つに絞って検証を省略しない。
3. **検証なしの報告**: 「直したはず」で終わらせず、可能な限り実際に確認する。
4. **原因不明のまま曖昧に流すこと**: わからない場合は「わからない」と明言し、次に確認すべきことを提案する。
